## Linux SRT temporary-filesystem canary correction — 15 October 2026

**Owner-host observation:** with Sandbox Runtime `0.0.79` and genuine `apply-seccomp` helper made visible, permitted workspace read PASS, private read-denial PASS and symlink escape denial PASS. However the original canary returned `FAIL: fake private path was writable` because an attempted `touch` inside a read-denied directory exited successfully. This is NOT evidence of a write to host data: [upstream SRT docs](https://github.com/anthropics/sandbox-runtime#filesystem-configuration) and [upstream issue #149](https://github.com/anthropics/sandbox-runtime/issues/149) explain that Linux `denyRead` directory paths may be hidden by a *writable ephemeral tmpfs* mount; the process may succeed without the output persisting to the real filesystem. The original test falsely conflated process exit code and host persistence.

**Source correction:** [PR #54](https://github.com/karanzing1992/engagement-core/pull/54) merged at commit `c635279f9669ba26f44b61d2cd78bb7809c97f1c`. Both installation and standalone retest canaries now require synthetic host-private files remain unchanged and absent, **and** require a separate read-visible but non-`allowWrite` path to reject writes. Repo-only QA [run 38712981982](https://github.com/karanzing1992/engagement-core/actions/runs/38712981982) succeeded. No SRT policy or native seccomp restriction was weakened. The production routing layer is still disabled without isolated identity and actual host canaries.

**Next evidence gate:** rerun [retest-srt-helper-visibility.sh](https://github.com/karanzing1992/engagement-core/blob/c635279f9669ba26f44b61d2cd78bb7809c97f1c/tools/claude-dev-router/retest-srt-helper-visibility.sh) on the owner's Linux PC using this pinned commit; only an observed `SRT_HOST_FILESYSTEM_CANARY_PASS` establishes synthetic filesystem pass.
