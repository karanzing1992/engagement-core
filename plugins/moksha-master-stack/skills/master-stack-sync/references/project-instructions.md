## FAST EXECUTION DEFAULT — large ChatGPT / AI-agent projects (16 October 2026)

This is an **efficiency layer**, not an exception to Golden Rules 0/0A, access-control, quality gates, auditability or production approval. It applies to project conversations and cooperating coding agents when this instruction is installed or explicitly referenced.

1. **Load minimum viable context.** Treat the ~210k-character Master technology registry as a source of truth, **not** a prompt to paste or read in full on every turn. Start with these concise Project instructions, the named project's current GitHub issue/PR/checkpoint, relevant README/source files and only the Master sections necessary for the specific action. Re-read source SHA/live status when freshness matters; never assume historical Master snapshots prove current device or production state.
2. **Use a task packet, not a long conversation replay.** Maintain the active task in the existing GitHub issue/PR, project checkpoint or approved queue: objective, affected repo/branch, owner/worker, dependencies, existing foundation/upstream reuse & rights, acceptance test, live-vs-source status, latest proof link, rollback and *single next action*. Keep packets compact (usually 300–600 words or fewer, excluding required evidence) without discarding safety detail.
3. **Separate QUICK and BUILD lanes.** QUICK = read-only status, diagnostics, short copy, narrow factual checks: one focused pass and concise factual answer. BUILD = research/reuse gate → bounded implementation in existing component → tests/QA → evidence → checkpoint. Do not run full architecture audits for routine status questions. Do not propose a new agent/queue/poller merely to make a chat faster.
4. **Parallelize only independent work.** Batch compatible independent reads and checks. Partition creation, coding, art, audio and QA by artifact/ownership, but serialize edits to the same file, shared browser/device control, production environment, credential store and any leased shared model quota. Never start duplicate tasks or competing shared Claude sessions. Observe existing worker capacities and authorizations.
5. **Checkpoints replace chat history.** At each significant milestone, failure, quota interruption or sluggish conversation, write a compact durable checkpoint in the **existing** tracking location: last verified commit/artifact and time; completed tests; current assignments; blockers and recovery attempts; unverified claims; next deterministic step. Resume in a fresh short project chat using the checkpoint URL and targeted supporting sources, not an unbounded transcript.
6. **Communicate outcome-first.** Report verified live results separately from source-only/queued/proposed work; include links/SHAs, actual blockers and the immediate next action. Avoid reprinting entire prior plans, repeating answered questions, speculative progress claims or needless tool calls. Provide concise progress during long tasks; an external worker doing work does not mean ChatGPT itself is running continuously.
7. **Recover before redesign.** On failure use the relevant existing runbook, bounded idempotent retry and rollback, then report/escalate with evidence if recovery fails. Preserve prior work, audit trail, paid-approval policy, and owner confirmation for irreversible operations.

**Limitations:** This text is repository source guidance. A commit **does not itself modify** a ChatGPT Project's live Instructions, speed settings, model choice or active chat context. Install the compact instruction in each applicable Project via its settings or use the authorized portable Skill; verify that it is actually available. It also does not create background agents, timers or an independent task system.
